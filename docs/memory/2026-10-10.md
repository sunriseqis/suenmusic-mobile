# 2026-10-10 鸿蒙端首轮排障：播控中心「显示上一首 / 未知曲目 / 歌词时有时无」

本轮工作跨两个仓库：

- `suenmusic-mobile` —— `hw/entry/src/main/ets/pages/Index.ets`（原生侧，主要改动）
- `suenmusic-server` —— `web/src/{native/audio.ts,native/update.ts,stores/lyrics.ts,views/Settings.vue}`（配套开关）

## 一、现象（用户报的）

1. 鸿蒙原生控件（锁屏 / 播控中心）**拉不到封面**
2. **歌词无法正常显示**；补充细节：**锁屏后解锁的瞬间能看到歌词，解锁后就不显示了**
3. 歌名显示为**「未知曲目」**
4. 补充细节：**切歌以后，歌曲信息还是上一首**

## 二、前情：先修的是「编译不过」

`build-hw` 在 `4d23276` 上 `CompileArkTS` 失败（`{ERROR:4 WARN:16}`，逐条对上 HEAD 的行号）：

| 报错 | 位置 | 根因 |
|---|---|---|
| `arkts-no-obj-literals-as-types` | 87:30 | `updateMetadata(meta: { assetId?: string; ... })` —— 匿名对象当类型 |
| `arkts-no-untyped-obj-literals` | 372:44 | **①的连带**：形参类型是匿名字面量类型时，调用点传的字面量也算"找不到声明类型" |
| `'wantAgent' has no exported member named 'WantAgent'` | 172:65 | `@kit.AbilityKit` 的 `wantAgent` 命名空间没导出这个名字 |

`backgroundTaskManager.startBackgroundRunning()` 的第三个参数就是那个未导出的类型，
`Object` 是父类型、传不进去，只会把"名字找不到"换成"类型不匹配"。

## 三、根因：三条链路在抢同一个 AVSession，且没有"谁最新"的秩序

关键前提：**一次切歌会并发触发多次上报** —— `web/src/stores/player.ts` 在加载流程里
（`syncMediaSessionMetadata`，约 670 行）调一次，`loadedmetadata` 事件里（约 520 行）又调一次；
而 JS 侧 `window.SuenHarmony.updateMediaMetadata(...)` 是**发完就不管**（不 await）。
所以换歌瞬间会有多个 async 调用同时在飞。

### 根因 1 —— 封面下载把元数据「堵在后面」（→ 显示上一首）

原 `updateMetadata` 的顺序是：**先 `await` 封面下载**（`downloadCoverPixelMap`，
`http.request`，`connectTimeout: 5000` + `readTimeout: 5000`），下载完才
`setAVMetadata`。于是：

- 标题被网络堵住，封面慢/失败时元数据要等满 10 秒才发出去；
- 上一首那次如果晚回来，就会**盖住**新歌 → 「切歌后仍显示上一首」。

### 根因 2 —— `updateLyric` **凭空伪造元数据**（→ 未知曲目）

原 `updateLyric` 在 `currentMetadata` 为空时会自己造一条：

```ts
const initMeta: avSession.AVMetadata = {
  assetId: assetId || 'suen_current',
  title: '未知曲目',
  lyric: lyricLrc
};
this.currentMetadata = initMeta;
await this.session.setAVMetadata(this.currentMetadata);
```

而 web 侧在 **App 启动（还没有当前曲目）、队列为空、切歌时**都会先推一条空歌词
（`web/src/stores/lyrics.ts` 的 `syncHarmonyLyric('', '')` / `(id, '')`）——
**App 一启动就必然命中这条**，播控中心于是被写上「未知曲目」，只能等真正的元数据来覆盖，
而那次未必到（见下）。

### 根因 3 —— `startsWith('suen_')` 这种"口令式"判断自相矛盾（→ 歌词时有时无）

原放行条件是：

```ts
if (!assetId || this.currentMetadata.assetId === assetId || this.currentMetadata.assetId.startsWith('suen_')) {
```

伪造出来的 assetId 恰好是 `suen_current`，**它自己就 `startsWith('suen_')`** ——
等于"任何曲目的歌词都收"，还会反复用这条假元数据 `setAVMetadata`。
另外 `updateMetadata` 的载荷里**根本没有 lyric 字段**
（`player.ts` 只发 `assetId/title/artist/album/coverUrl/durationMs`），
它想"保住"歌词全靠 `currentMetadata.assetId === meta.assetId` 这个相等判断 ——
而在伪造的 `suen_current` 面前这个判断是坏的。

### 顺带：`!this.session` 的静默丢弃

原 `updateMetadata` / `updateLyric` 开头都是 `if (!this.session) return;` ——
session 还没建好就**静默丢弃，一行日志都不打**。这是本轮最难查的原因之一。

## 四、修法（`suenmusic-mobile` 的 `fix(hw)` 提交）

`Index.ets`：

1. **先推文本、后补封面**：`updateMetadata` 立刻用标题/歌手/专辑/时长调一次
   `setAVMetadata`，封面交给新的 `attachCover(cover, seq)` **异步**补。
2. **单调序号守卫**：类里新增 `metaSeq`；每次上报 `++`，异步结果回来时
   `seq !== this.metaSeq` 就**丢弃并 `release()` 那张 PixelMap**（旧封面不许盖新歌）。
3. **歌词不再伪造元数据**：新增 `currentLyric` 单独存储；`currentMetadata` 为空时
   **只存歌词、不碰系统 UI**，等元数据到达时一并推。另新增 `currentAssetId`。
4. **assetId 换曲即作废**：`assetId` 变化时同时清掉旧歌词与旧封面 URL；
   歌词只在 `assetId` 等于当前曲目时才收；`assetId` 为空只清歌词、**不动标题封面**；
   不匹配则记日志说明原因。
5. **失败可观测**：`downloadCoverPixelMap` 增加
   `expectDataType: http.HttpDataType.ARRAY_BUFFER`，并把三种失败分别打日志
   （非 200 / 拿到非二进制 / 解码异常），成功也打一行；`!session` 一律 `hilog.error`。
   `httpRequest.destroy()` 挪进 `finally`。

`web`（`suenmusic-server`）：

6. 新增鸿蒙「**系统歌词**」开关（见 `MEMORY.md` 第 45 条），默认开；关掉时走
   **force 路径**把已经推出去的歌词收回。
7. `native/update.ts` 新增 `isHarmony = !!window.SuenHarmony` —— 鸿蒙端不走 Capacitor，
   `isAndroid/isIOS/isNativeAudio` 在那边全是 false（见 `MEMORY.md` 第 41 条）。

## 七、一句话教训

**给系统 UI 推数据时，"谁最新"必须有显式秩序（序号守卫），"缺数据"时绝不伪造内容，
"走网络的那一步"永远不能挡在"先让用户看到正确信息"前面。**
这三条在本轮各对应一个症状，而且它们叠在一起才让现象变得像"随机"。

## 八、后续：同一轮内的修正 —— 控件「完全消失」与上面第 3 条的教训

上面那个"歌词不再伪造元数据、等 updateMetadata 到达再推"的写法**本身是对的，但不够**。
用户装上新包后报：**播控中心那条控件完全消失了**。

**定案过程（A/B 排除）**：

| 观测 | 推论 |
|---|---|
| 用户确认 **App 界面完全正常** | 页面加载正常 → HAP 里的 rawfile 是全的 → 不是"web 没打进包" |
| 以前歌词能看到 | `updateLyric` 这条路能通 |
| 以前标题是「未知曲目」 | 控件**完全是靠歌词路径伪造的那条元数据撑着**的 |
| → 结论 | **`updateMediaMetadata` 这条在鸿蒙端从未真正生效**（具体是哪一步挡住了没有定论：旧代码在这一步有**两处静默** —— `if (!this.session) return;` 与 `await 封面下载` 5s+5s） |

所以"控件消失"不是新 bug，而是**去掉拐杖后暴露了既有 bug**；但用户侧的结果一样，
这是本轮的失误 —— **去掉一根拐杖之前，要先确认另一条腿能承重。**

**改法（把责任交给"已被证实能通"的那条路，并让两条路互不依赖）**：

- web `stores/lyrics.ts`：歌词消息**带完整元数据**
  （`assetId/title/artist/album/coverUrl/durationMs/lyric`，从 `player.currentTrack` 组装）。
- hw `Index.ets`：`updateLyric` 改收完整载荷，走同一条 `doUpdateMetadata`
  （推文本 → 带歌词 → **异步**补封面）；同一首则只更新歌词；无依据只暂存、**仍不伪造**。
  两个方法都包 try/catch（JS 桥不 await，异常不能抛回桥）；
  不再释放"已交给系统"的 PixelMap（只释放从未交给系统的那张）；
  两条 `收到…上报:` 入口日志 —— 下次一眼看出**哪条消息真的到了**。

**仍未证实**：`updateMediaMetadata` 到底有没有被 web 调用过（日志会回答）。
若确认从未被调，那条路可以删掉；现在留着无害。

**兜底**：若这次仍不行，回退原生侧到 `bae9b6c`（控件至少还在），再小步试。

## 九、真正的根因：`undefined` 的键让整条元数据推送被静默拒绝

上面 §八 定位到"`updateMediaMetadata` 从未生效"，但**当时仍不知道它为什么没生效**。
真正的答案在又一轮试错之后才浮出来。

**回溯"唯一被证实成功过的那次调用"** —— 这是解开这个僵局的关键一步：

| 观测 | 含义 |
|---|---|
| 歌名显示「未知曲目」 | 那条**兜底伪造**的数据是播控中心里唯一的内容 |
| 歌词曾经能显示 | 伪造数据里 `lyric` 是**真字符串** |
| 封面永远拉不到 / 切歌后仍显示上一首 | 真正的元数据**一次都没成功过** |
| 拿掉伪造后控件完全消失 | 现在每次调用都带 `undefined` → **全被拒** |

于是结论：**`AVMetadata` 里值为 `undefined` 的键会让 `setAVMetadata()` 被拒绝**。
伪造数据之所以能成功，正因为它**一个 undefined 字段都没有**。

**修法**：有值才赋键；清空歌词用空字符串。
```ts
const metadata: avSession.AVMetadata = { assetId, title, artist, album, duration };
if (this.currentLyric) { metadata.lyric = this.currentLyric; }
if (this.currentPixelMap) { metadata.mediaImage = this.currentPixelMap; }
```
另外 `init()` 里会话建好后先推一条**只有应用名**的最小元数据，保证控件先出现
—— 写 `SuenMusic` 而不是编一个歌名：不知道就不知道，别骗系统。

**这条为什么值得单独记一条（MEMORY 第 46 条）**：四个报障、一个根因，而且
`catch` 里明明有 `hilog.error`，只是没人能看到 —— **"打了日志但没人能看"等价于没有日志**。

## 十、第二个问题：锁屏歌词的时间轴比实际快 20 秒

**现象**：控件里实际唱到 10 秒、歌词却滚到 30 秒；**手动上拉能看到正确的时间轴，
松开又弹回错误位置** —— 说明歌词内容与时间戳都对，错的是系统推算的"现在播到哪"。

**根因**：锁屏歌词的滚动位置由 `AVPlaybackState.position`（`elapsedTime` + `updateTime`）
**外推**得出。而 web 侧只在**状态变化**时上报位置，`timeupdate` 只更新了 store：
```ts
el.addEventListener('timeupdate', () => { positionMs.value = Math.round(el.currentTime * 1000); });
```
更要命的是 **`applyPendingSeek()`（续播跳转，`player.ts:274`）直接改 `el.currentTime`、
不经过 `seek()`**，因此不上报 → 锚点 stale → 误差累积。

**修法**：`timeupdate` 里按 **1 秒节流**补一次上报（仅播放中）。锁屏时 `timeupdate`
依然触发（媒体事件不受 JS 定时器节流影响）。

**顺带一个思路**：`updateTime` 的单位至今没确认（SDK 约定查不到），这次**刻意不改**——
因为"1 秒重新锚定"已经让这个不确定性无关紧要。**架构上的选择可以消掉信息缺失**，
这比先去查文档更划算（MEMORY 第 47 条）。

## 十一、这一轮的整体教训

1. **别让系统猜数据**（第 47 条）：凡是能由我们推的，就周期推，别指望对方外推。
2. **给系统 API 的结构体不要塞 `undefined`**（第 46 条）：会被静默拒绝，且日志看不见。
3. **去掉一层兜底之前，先确认另一条路真的能承重**（第 48 条）：本轮为此让用户多编译了两次。
4. **诊断靠自己回溯"唯一成功过的样本"**，而不是通读代码找 bug —— 通读代码会找出三个
   真问题（封面 await 阻塞、伪造元数据、口令式 assetId 判断），但**都不是根因**。

**验收状态（2026-10-10）**：播控中心控件恢复正常、歌词时间轴与实际播放对齐，
用户反馈"基本完美"。封面与歌词显示的细节尚未逐条复验。
**下一步**：桌面服务卡片（全新 ExtensionAbility，见下）—— 尚未开工。
