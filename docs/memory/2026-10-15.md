# 2026-10-15 卡片按钮失效排障 + AVSession 自愈

## 一、事故与根因

10/12 交付 v5 卡片后用户实测报障：**应用后台静默一段时间后，桌面卡片
播放键点了出声（老构建）/ 没反应（CI 构建），播控中心控件消失，
卡片暂停/切歌失效**。本次定位到两条独立根因：

### 根因 1（P0）：web 侧 `__suenAudioControl` 从来没有 `toggle` / `toggleFavorite`

- 卡片（v4/v5）播放键发 `toggle`、红心发 `favorite`；PlayerControlHub 把
  `favorite` 映射成 web 的 `toggleFavorite()`。但 web 注册的
  `__suenAudioControl` 只有 `play/pause/stop/next/prev/seek` ——
  `runJavaScript` 里 `window.__suenAudioControl.toggle()` 直接 TypeError，
  **静默失败**（catch 里只有 hilog，界面上毫无反馈）。
- 后果：**所有 CI 构建的 HAP，卡片播放键与红心键都是死的**。CI 的 web
  产自 suenmusic-server 私有仓库 main，而 main 从未包含这次改动。
- 取证反转（10/15 晚补正）：C 盘工作区 `git log -S 'toggleFavorite'` 空、
  `git fsck --dangling` 无悬空对象，当时结论"改动从未提交"。**实际是**：
  用户 10/12 就在 D 盘仓库（GitHub Desktop 管理的
  `D:\github\suenmusic\suenmusic-server`）提交了 `0699613 适配鸿蒙卡片页`
  （player.ts + main.ts + favorites.ts 三文件，toggle/toggleFavorite/
  favorite 上报全套），**只提交未 push** —— 远端 main、C 盘工作区、CI
  全都没有它。教训单独立条（MEMORY §56）。

### 根因 2：AVSession 挂起期间被系统去激活/销毁，恢复后无自愈

- 官方 FAQ（faqs-avsession-23）+ 长时任务文档：
  - 后台音频被系统冻结/打断后，**系统会自动停掉长时任务**；
    重启播放需**再次申请**。
  - 播控中心控制命令要 **AVSession 激活后生效**；会话被销毁时
    所有 set* 调用报 **6600102 "The session does not exist"**。
  - 不满足接入规范（AVSession 非激活态）的后台播放会被**静音并冻结**，
    切回前台才解除 —— 与"恢复后只播一两秒就停"吻合。
- 原代码 `activate()` 只在 `init()` 调一次，挂起数小时后会话可能已被
  系统去激活甚至销毁，恢复播放后没有任何重新激活/重建逻辑 →
  播控中心控件消失、锁屏按钮失灵。

## 二、修复内容

### web（suenmusic-server）—— 以用户 10/12 的 `0699613` 为准

1. `main.ts` 启动时 `registerGlobalAudioControl()`：`__suenAudioControl`
   全局注册、走 store 公开 API —— **冷启动窗口（恢复会话还没播过）原生
   按播放不再是空操作**；`toggle()` 内部用 `ensureAudio()` 而非缓存 audio，
   同样为冷启动兜底。
2. `favorites.ts`：`reportHarmonyFavorite()` —— 收藏切换成功/回滚后把
   `{assetId, favorite}` 报给 `SuenHarmony.updateFavorite`（原生按
   assetId 匹配当前曲，不匹配直接忽略）。
3. `player.ts`：`updateMediaMetadata` 载荷补 `favorite` 字段；收藏集合
   未就绪时元数据里可能是假 false，`ensureLoaded().then` 补报一次纠偏。
4. 10/15 AI 在 C 盘独立实现的 watch 双源上报版**作废**（注册挂在
   `setupMediaSessionControls`、`toggle()` 用缓存 audio —— 恰好有两个
   冷启动缺陷，0699613 都修了）。C 盘工作区已从 D 盘同步这三个文件。

### native（hw `entry/src/main/ets/pages/Index.ets`）

1. `reactivateSession()`：`updatePlaybackState` 里 paused→playing
   转换时调用 `session.activate()`（幂等）；activate 报 6600102 → 重建。
2. `rebuildSession()`：销毁旧句柄（失败属预期，吞）→ 重新
   createAVSession + activate + `registerSessionListeners` →
   重放缓存的 `currentMetadata` 与播放态。`rebuildingSession` 标志
   防递归。6600102 时下一个 ~1s 进度上报自然补回最新状态，无需手动重试。
3. `updatePlaybackState` 的 catch 里识别 6600102 → `rebuildSession()`。

## 六、弱网/切网/热启动长时间卡顿 — 诊断结论与修复计划（待执行）

> 状态：方案已定，**范围待用户确认**（只做 P0 web 四项 / 连 P1 iOS
> 一起）。本节为完整计划存档，防止上下文丢失；执行时按此逐项落地。

### 问题定性

**是设计缺陷，不是网络问题**。出门切网后热启动（应用从后台恢复）
长时间卡住、杀进程重开反而快——因为冷启动会跑 `selectBestServer()`
（`main.ts:87`），而热启动**没有任何重选触发点**：

- `online` 事件监听在 `main.ts:90`，切网时大多不触发；
- `visibilitychange` / `pageshow` 全项目零注册；
- `bridge.ts:319` 的 `isNativeAudio` 守卫导致鸿蒙端连原生
  networkChanged 都不注册（鸿蒙 `isNativeAudio=false`，音频走
  ArkWeb WebView 内 HTMLAudioElement）。

结果：换网后所有请求继续打旧地址，每个都吃满默认超时才 failover。

### 证据链（四处叠加）

1. **热启动无重选**（见上）。
2. **快速失败判定太窄**：`client.ts:374-390` `isPrivateIpUrl` 只认
   IPv4 私网段（192.168/10/172.16-31）。IPv6 ULA（fd/fc/::1）、
   反代域名、CF 隧道全按公网处理 → 吃满默认 20s
   （`client.ts:30` `DEFAULT_TIMEOUT_MS`）+ refresh 15s
   （`client.ts:462`）。
3. **probeStream 超时是真 bug**：`player.ts:624-654` 创建了
   AbortController 但**没挂定时器**，弱网下挂到 WebView 默认超时
   （iOS 可达 60s）。
4. **iOS 原生侧**：`SuenAudioCache.swift:339`
   `timeoutIntervalForRequest=30s`，挂起恢复后 stalled 的 range
   request 干等 30s 才 retry（`:375`）。

### 出门热启动卡顿时间线（量化）

普通请求 20s 超时 → failover（探测旧地址 1s + 并行探测其余 3s）→
切 CF → 重放 ≈ **25s**；若 access token 恰好过期（服务端 TTL 2h，
`config.ts:116`）再叠加 ≈ **40s**。

### 修复方案

#### P0：web 四项（全端生效，鸿蒙覆盖在内）

1. `main.ts`：注册 `visibilitychange` + `pageshow` →
   `onNetworkEnvironmentChanged()` —— 热启动/回前台即触发重选。
2. 多候选时默认超时 20s→**8s**、refresh 15s→**8s**。
3. `probeStream` 补 **8s** 超时（AbortController 挂 setTimeout，
   原来没挂，真 bug）。
4. `isPrivateIpUrl` 补 IPv6 ULA（`fd`/`fc` 前缀）与 `::1`。

#### P1：iOS 原生

- 回前台 / 网络路径变化（`SuenAudioPlugin.swift` NWPathMonitor
  `:1300`、networkChanged emit `:110-112`）时，中止在途 stalled
  上游请求并立即 retry，不等 30s（`SuenAudioCache.swift:339/:375`）。

### 安全性论证（降超时为何不误伤慢接口）

resolve 30s、search 25s、AI 30-600s、import 30-120s 均有显式
`timeoutMs`，只有轻量接口用默认值 —— 降默认值只影响"该快而快不了"
的坏路径。

### 换路后的衔接（无需新代码）

`player.ts:1874` `onBaseUrlChanged` 已有重载当前曲 + 续播逻辑
（原生端 `bridge.rebindBaseUrl` + `syncNativeQueue`），web 重选
修复完成后自动接上。

### 约束（必须遵守的历史决策）

- failover 策略（2026-09-14 用户拍板）：保守（当前可用不切回）、
  启动时探测一次、运行期失败才切；`FAILOVER_COOLDOWN_MS=3000`；
  探测超时首候选 1.5s 其余 3s。新触发点不得绕过 cooldown。
- 三端音频拓扑：Android/iOS 走 Capacitor 原生（Media3 /
  SuenAudioPlugin+AVPlayer+SuenAudioCache）；鸿蒙端音频走
  ArkWeb WebView —— **web 修复全覆盖鸿蒙**。
- ArkTS 规约：禁 `as` 断言（catch 后 `BusinessError` 例外）。

### P1 iOS 落地细节（执行时定稿）

1. `SuenAudioCache.swift` `StreamCacheDownloader` 新增 `retryNow()`：
   仅当在途请求**真正卡住**（>1.5s 无数据，`lastDataAt`/`stallThreshold`
   判定）才 `task.cancel()`；`manualRestart` 标记让 `didCompleteWithError`
   走「立即续拉」分支且**不消耗** `maxAttempts=4` 预算；cancel 恰好落在
   收尾瞬间（`reachedTotal`）则直接按完成收尾。防抖：触发时刷新
   `lastDataAt`，连发事件（切网抖动）不会反复打断新请求。
2. `AudioCacheStore.retryStalledDownloads()`：`dictLock` 下快照
   `downloaders.values`，逐个 `retryNow()`。
3. `SuenAudioPlugin.swift` 触发点两个：`networkChanged == "available"`
   （断网恢复/切网）+ `UIApplication.didBecomeActiveNotification`（回前台）。
   Web 端重探测由 visibilitychange/pageshow 自理（P0-1），两边互不依赖。
4. `NetworkMonitor` 补**接口类型变化**检测（`availableInterfaces.first?.type`）：
   WiFi↔蜂窝切换时 `satisfied` 始终为 true，原实现报不出"切网"事件 ——
   这是 P1 方案里隐含的前提，落地时补上的。
5. iOS 改动无法在 Windows 本地编译，语法靠精读自检；待用户 Xcode/CI 编译。
6. `maxAttempts=4` 语义不变：仍是「连续中断 4 次放弃」，手动重启不占预算。
